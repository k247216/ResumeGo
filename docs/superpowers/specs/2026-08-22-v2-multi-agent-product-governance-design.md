# Career OS V2 多 Agent 产品治理设计

Status: Approved direction, pending implementation documents

Date: 2026-08-22

## 1. 目标

建立一套由总控 Agent 负责产品设计、架构边界、任务拆分、集成审查和最终测试，功能 Agent 负责边界明确的小功能实现的协作机制。

该机制解决的核心问题不是“如何让更多 Agent 同时写代码”，而是：

- 如何保证并行实现仍然服从同一个 Career OS 产品模型；
- 如何避免多个 Agent 同时修改公共接口、数据库迁移和核心规则；
- 如何让每个交付都具有可重复验证的验收证据；
- 如何确保只有经过统一审查和全量测试的功能才能进入 V2 主开发线。

## 2. 治理模型

采用中央总控、隔离实现、统一集成的模式。

### 2.1 总控 Agent

总控 Agent 是 V2 开发的产品与技术决策中心，负责：

- 维护冻结产品模型、路线图和模块边界；
- 决定功能是否进入当前阶段；
- 把产品目标拆成可独立交付的任务卡；
- 冻结任务所依赖的公共接口和基础提交；
- 指定功能 Agent 可以修改的文件；
- 审查数据模型、隐私边界、失败路径和测试证据；
- 退回能够运行但不符合产品或工程要求的实现；
- 负责跨分支集成、全量回归、桌面构建和发布前验证。

总控 Agent 不以“代码已经完成”为合入依据，而以用户结果、领域一致性、数据安全、可恢复性和验证证据为合入依据。

### 2.2 功能 Agent

功能 Agent 只实施任务卡明确授权的功能，不拥有产品范围和公共架构的解释权。

功能 Agent 必须：

- 从任务卡指定的提交建立独立 worktree 和短期分支；
- 只修改允许文件；
- 先验证失败测试，再实施最小功能；
- 运行任务要求的局部和模块级回归；
- 以标准交付报告提交变更、测试证据、风险和未完成事项；
- 在发现边界不足时停止并申请总控决策，不得自行扩展范围。

## 3. 分支和集成策略

V2 当前集成分支为 `codex/v2-career-os`。功能分支采用：

```text
codex/v2-<任务编号>-<功能简称>
```

每个功能 Agent 使用独立 worktree。功能 Agent不得直接修改 `main`、V1 维护线或 V2 集成 worktree，不得自行合并、变基或覆盖其他分支。

功能分支完成后只交付提交哈希。总控 Agent在确认基础提交、变更范围和测试证据后决定是否集成。出现公共契约冲突时，由总控 Agent重新分派或调整顺序，功能 Agent不自行解决跨任务冲突。

## 4. 权限边界

任务卡必须列出允许创建、修改和测试的文件。未列出的文件默认禁止修改。

以下内容由总控 Agent默认控制，只有任务卡明确授权时才能修改：

- H2 和 MySQL 数据库迁移；
- 公共 DTO、API 类型和跨模块 Port；
- 领域枚举、状态机和确定性业务规则；
- Electron 应用身份、数据目录和升级协议；
- 全局依赖、构建与打包配置；
- 产品模型、路线图、架构、隐私和重大决策文档。

功能 Agent发现必须越过权限边界时，必须报告原因、目标文件、契约影响、替代方案和依赖任务，然后等待重新授权。

## 5. 产品守卫

所有任务必须服从以下价值链：

```text
Knowledge Base
      ↓
Career Pipeline
      ↓
Resume Version
      ↓
Interview Engine
      ↓
Growth Feedback
      ↓
Workspace Action
```

进入开发前，总控 Agent必须确认：

1. 功能是否让职业资产在真实流程中被复用；
2. 数据来源、所有权、删除和迁移行为是否明确；
3. AI 未配置或失败时，本地核心流程是否可用；
4. 是否能用虚构测试夹具验证，而不使用真实个人数据或模型服务；
5. 是否保持 V1/V2 并行安装和当前阶段可恢复升级。

禁止把 Workspace 变成全功能 Dashboard、把 Pipeline 变成知识容器、让 AI 控制阶段或最终事实、写死虚假联动数据，以及擅自加入岗位爬虫、自动投递和全面 UI 重做。

## 6. 标准任务卡契约

每张任务卡必须包含：

- 任务编号和名称；
- 用户结果；
- 当前阶段和优先级；
- 指定基础提交；
- 输入、输出和依赖；
- 范围内与范围外事项；
- 允许修改、创建和测试的文件；
- 不允许改变的公共契约；
- 数据、隐私和 AI 影响；
- 正常、空、失败、恢复和越权行为；
- 必须先失败的测试；
- 局部、模块和构建验证命令；
- 交付报告格式；
- 总控 Agent的合入条件。

任务卡不能使用“适当处理”“补充测试”“按现有方式”等模糊描述。接口名称、状态、错误行为和验收输出必须能够被独立执行者直接理解。

## 7. 功能分支登记

仓库维护一份 V2 功能分支登记表，每个任务记录：

- 任务编号；
- 所属里程碑；
- 负责人；
- 基础提交；
- 分支名；
- 文件所有权；
- 契约依赖；
- 状态；
- 最终提交；
- 审查结论；
- 集成提交。

同一时间不允许两个进行中的任务拥有同一公共文件。文件所有权冲突必须在编码前解决。

## 8. 交付与审查

功能 Agent交付时必须报告：

- 完成内容；
- 修改文件；
- 新增或改变的接口；
- 真实测试命令、退出结果和数量；
- 数据库影响；
- 隐私与 AI 影响；
- 未完成事项；
- 已知风险；
- 需要总控 Agent决定的问题。

总控 Agent按以下顺序审查：

1. 对照任务卡确认范围；
2. 检查产品模型和模块归属；
3. 检查数据所有权、删除、事务和迁移；
4. 检查正常、空、失败、恢复和越权路径；
5. 检查测试是否真正覆盖用户可观察行为；
6. 在干净环境复跑目标测试；
7. 决定通过、带条件通过或退回。

任何未解释的额外文件、公共契约漂移、缺失失败路径、伪造联动、敏感数据、未经校验的 AI 写入和不完整测试声明都会直接退回。

## 9. 最终测试责任

功能 Agent只证明自己的功能分支满足任务卡。总控 Agent负责证明集成后的产品仍然成立。

最终测试矩阵分为：

- 后端：单元、Repository、迁移、事务、Controller 和全量 `mvn test`；
- 前端：组件、store、API 状态和全量 `npm test`；
- 构建：`npm run build` 与 `npm run build:electron`；
- 桌面运行：首次启动、后端子进程、数据目录、关闭和重启；
- 数据：空工作区、V1 只读导入、失败回滚、升级后重开和备份恢复；
- 核心流程：多 Pipeline、简历版本、日程、模拟面试、知识资产和下一步行动；
- 安全隐私：日志、密钥、路径、真实数据和外部调用检查。

测试结果必须记录实际命令、退出码、测试数量、构建产物和已知问题。部分测试不能被表述为全量通过。

## 10. 需要生成的治理资产

本设计确认后，实施阶段生成以下仓库文件：

1. `docs/architecture/agent-collaboration.md`：正式协作与权限规范；
2. `docs/product/workstreams.md`：V2 功能流、任务状态和依赖登记；
3. `docs/templates/v2-feature-task-card.md`：可复制给功能 Agent 的详细任务卡；
4. `docs/templates/v2-agent-delivery-report.md`：统一交付报告；
5. `docs/testing/v2-integration-review-checklist.md`：总控集成审查清单；
6. `docs/testing/v2-final-test-matrix.md`：阶段和发布级最终测试矩阵；
7. `docs/decisions.md`：记录中央总控、多分支隔离和统一集成的长期决定。

## 11. 成功标准

治理机制实施完成后应满足：

- 用户可以把标准任务卡直接交给任一功能 Agent；
- 功能 Agent不需要重新解释产品方向即可开始；
- 两项并行任务不会默认修改同一公共契约；
- 每项交付都有可重复测试证据和明确风险；
- 总控 Agent可以依据统一清单决定接收或退回；
- V2 集成分支始终保持可构建、可测试和可继续迁移；
- 最终测试责任不会因功能被分派而分散或消失。
