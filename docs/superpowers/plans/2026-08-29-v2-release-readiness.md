# 职达 Career OS V2.0 发布准备实施计划

> **For agentic workers:** Use this plan to完成发布前的验证、文档和集成；每个任务完成后都要保留可复核证据。

**目标：** 在不改变当前 V2 产品边界的前提下，逐页验证可用流程，整理真实已实现能力，补齐 GitHub 项目说明与开源许可证，并以 `v2.0.0` 创建可追溯的 GitHub Release。

**架构基线：** 前端工作台通过路由进入工作台、求职管线、知识库、简历库、面试、日程和设置；面试引擎按主页、练习准备、面试房间、复盘报告分层；Pipeline、Resume Version、Knowledge Document 仍是独立对象，面试开始时冻结上下文快照。

**技术栈基线：** Vue 3 + TypeScript + Vite + Pinia + Element Plus + Vitest；后端使用 Spring Boot + MyBatis（以仓库实际构建文件为准）；桌面端使用仓库现有 Electron/打包脚本（以实际脚本为准）。

## 全局约束

- 只把已经在代码、测试或可复现页面流程中确认的能力写入 README 和 Release Notes。
- 不把 API Key、面试回答、联系方式或其他个人数据写入日志、文档样例或提交记录。
- 保持本地优先和现有数据边界；不在发布准备阶段引入新的云端传输或自动投递能力。
- 不使用破坏性 Git 操作；保留其他 agent 的现有改动。
- 发布前必须通过 `git diff --check`、前端测试、前端构建和后端测试（若后端构建环境可用）。

## 任务 1：核对仓库与发布基线

**文件：** `docs/architecture/baseline.md`、`docs/product/productV2.md`、`docs/product/roadmap.md`、根目录及子项目构建文件

**步骤：**

1. 确认当前分支、工作区改动、远端 URL、最新提交和现有版本号。
2. 盘点实际路由、页面、启动命令、构建命令、桌面打包入口和已有许可证。
3. 仅以当前仓库可验证内容确定 V2.0 发布范围，记录已知限制。

**完成标准：** 发布文档中的能力、命令和链接均能在仓库中找到对应依据。

## 任务 2：逐页功能回归与构建验证

**文件：** `docs/releases/v2.0-test-report.md`

**步骤：**

1. 对工作台、求职管线、知识库、简历库、面试主页、三种练习准备页、面试房间、复盘、日程和设置执行路由级 smoke check。
2. 运行前端全量测试并记录测试文件数、用例数和仅影响测试环境的既有警告。
3. 运行前端生产构建；运行后端测试或记录阻塞原因；执行 `git diff --check`。
4. 只记录会阻断用户流程的问题，不因无关网络告警扩大测试范围。

**完成标准：** 报告区分“通过”“已知限制”“环境阻塞”，不使用无证据的完成表述。

## 任务 3：编写 GitHub README 与许可证

**文件：** `README.md`、`LICENSE`

**步骤：**

1. 按常见开源项目结构写产品定位、V2.0 能力、核心流程、技术栈徽章、快速开始、开发与测试命令、桌面打包、隐私边界和贡献方式。
2. 使用项目真实远端地址生成 release、issues 和 license 徽章。
3. 若仓库没有现有许可证，加入标准 MIT 许可证并在 README 中明确说明。

**完成标准：** 新用户可只凭 README 启动本地开发环境，且不会被承诺未实现的功能误导。

## 任务 4：整理 V2.0 Release Notes

**文件：** `docs/releases/v2.0.0.md`

**步骤：**

1. 以用户视角说明 V2.0 解决的问题、已交付模块、主要使用流程和本地优先原则。
2. 明确 API 配置、数据来源、面试上下文快照、三种训练模式和页面级验证结果。
3. 列出已知限制、后续路线和不属于本版本的能力，避免把路线图写成现成功能。

**完成标准：** Release Notes 与 README、测试报告和代码行为一致。

## 任务 5：提交、打标签并发布

**文件：** 上述发布文档及本次应纳入 V2.0 的已验证代码

**步骤：**

1. 复核工作区变更范围、测试证据和文档链接。
2. 创建一个范围明确的发布提交，创建 `v2.0.0` 标签并推送到当前项目远端的 `main`。
3. 使用 GitHub CLI 以 `docs/releases/v2.0.0.md` 创建标题为“职达 Career OS V2.0”的 Release。
4. 发布后读取远端 Release 和 tag，确认链接可访问。

**完成标准：** GitHub Release、tag、README、LICENSE 和测试报告互相可追溯；若认证或远端权限阻塞，保留本地可发布提交并明确报告阻塞点。
