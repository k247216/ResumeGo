# Career OS V2 功能分支集成审查清单

用途：Core Controller 对外部 Agent 的最终提交做统一接收或退回判断。审查对象是“任务卡 + 交付报告 + 提交差异 + 可复现验证”，不是 Agent 的口头总结。

## 1. 输入材料

- [ ] 任务卡路径和 Task ID 明确，任务开始时状态为 `READY`。
- [ ] 交付报告使用 `docs/templates/v2-agent-delivery-report.md`，字段没有省略。
- [ ] 提供 Base commit、功能分支、Final commit 的完整哈希。
- [ ] Final commit 可从 Base commit 追溯，且未混入其他任务提交。

建议核验：

```bash
git merge-base --is-ancestor <BASE_COMMIT> <FINAL_COMMIT>
git diff --name-status <BASE_COMMIT>..<FINAL_COMMIT>
git log --oneline <BASE_COMMIT>..<FINAL_COMMIT>
git diff --check <BASE_COMMIT>..<FINAL_COMMIT>
```

## 2. 权限与范围

- [ ] 所有新增、修改、删除文件都位于任务卡 `Allowed files`。
- [ ] 额外文件存在 Core Controller 的书面重新授权或新任务卡；“实现需要”不算授权。
- [ ] 未修改 V1、`main`、V2 集成 worktree 或其他 Agent 分支。
- [ ] 未触碰未授权的迁移、共享 DTO、跨模块 Port、状态机、Electron 身份、构建配置和产品/架构文档。
- [ ] 没有把范围外工作藏在格式化、重命名或依赖升级中。

任一未授权改动无法移除时，结果直接为 `REJECT`。

## 3. 产品与公共契约

- [ ] 用户可观察结果与任务卡一致，没有用演示数据伪装联动。
- [ ] Scope out 中的行为没有被偷偷实现。
- [ ] HTTP method/path/status、DTO 字段、可空性、枚举和错误语义没有漂移。
- [ ] Knowledge Base、Pipeline、Resume、Interview、Growth、Workspace 的领域边界未被重新解释。
- [ ] Pipeline 目标切换没有隐式污染独立简历资产；绑定只在明确契约中发生。

公共契约发生合理变化也不能直接接收：先停止集成，更新决策/依赖任务，再重新发卡。

## 4. 数据、事务与恢复

- [ ] 当前用户所有权在读取和写入路径均被验证，跨用户资源表现为不可用。
- [ ] 多步写入具有明确事务边界；失败不会留下半完成状态。
- [ ] 删除是明确的软删除、解除关联或硬删除语义，没有静默级联。
- [ ] append-only 历史没有编辑或覆盖入口。
- [ ] Schema 变化具备被授权的迁移、升级测试和回退/备份说明。
- [ ] 重启、重新打开、归档/恢复等持久化行为按任务需要验证。

## 5. 隐私与 AI

- [ ] 仓库、测试、快照和普通日志不包含真实简历、联系方式、面试回答、令牌或模型密钥。
- [ ] 测试夹具为虚构数据。
- [ ] 新增第三方传输、遥测或云存储前已经更新隐私决策并获得授权。
- [ ] AI 输出经过结构化校验，保留原文、依据、建议稿和用户决定。
- [ ] AI 不直接控制权限、最终分数、岗位排序或 Pipeline/面试流程状态。

可使用：

```bash
git diff <BASE_COMMIT>..<FINAL_COMMIT> -- . ':!*.lock'
```

人工检查潜在密钥、个人邮箱、手机号和请求/响应日志；不得将扫描无命中等同于完整隐私证明。

## 6. 测试证据

- [ ] RED 在生产代码前真实发生，并记录命令、退出码、测试数和失败原因。
- [ ] GREEN 覆盖任务卡全部正常、空、失败、恢复和越权场景。
- [ ] 局部测试和模块全量回归分别记录，未混淆。
- [ ] 构建命令在任务要求时实际执行。
- [ ] 未执行项明确写为未执行，没有被表述为通过。
- [ ] 审查者至少独立复现任务卡的局部测试和受影响模块全量测试。

只提供截图、终端片段或“测试通过”文字，不足以接收。

## 7. 代码质量

- [ ] 改动是满足契约的最小实现，没有重复数据源或绕过已有抽象。
- [ ] 错误被呈现或传播，没有空 catch、静默 fallback 或假默认值。
- [ ] 命名表达 V2 领域语义，没有把 Legacy Job Project 当成 Pipeline。
- [ ] 不存在临时开关、硬编码用户内容、调试日志或无使用代码。
- [ ] 测试断言用户/契约行为，而非只验证 mock 调用次数。

## 8. 集成前后

集成前：

- [ ] V2 集成 worktree 干净。
- [ ] 功能分支基线仍与登记表一致；若集成分支前进，已评估冲突和契约变化。
- [ ] 与其他待集成任务无文件所有权冲突。

集成后：

- [ ] 运行受影响模块全量测试。
- [ ] 运行前端生产构建；涉及桌面边界时运行 Electron 构建。
- [ ] 更新 `docs/product/workstreams.md` 状态、集成提交与后续任务真实基线。
- [ ] `git diff --check` 通过，`git status --short` 仅包含预期状态。

## 9. 审查结果

只能选择一种：

- `APPROVED`：全部强制门禁通过，可进入 V2 集成分支。
- `CONDITIONAL`：仅非阻塞文档/命名小项，明确修正清单和再次核验范围；不能在未修正时发布。
- `REJECT`：越权、契约漂移、数据/隐私风险、缺失关键行为或测试证据不可信。列出阻塞项并退回原 Agent。

审查记录必须包含 Task ID、Base/Final commit、复现命令与结果、发现分级、最终结论和集成提交（如有）。
