# ResumeGo 开发与完成标准

## 工作原则

- 先写清楚用户结果、范围和验收方式，再修改代码。
- 一次变更只解决一个明确问题，避免顺带扩展产品范围。
- 优先修复核心闭环，再处理装饰性功能。
- AI 生成或修改的内容必须经过人工理解、差异检查和验证。
- 发现重复问题时，优先转化为测试、类型约束或稳定文档。

## Git

`main` 是唯一长期分支，并始终保持可构建、可测试。

较小、可快速验证的个人变更可以直接在本地完成；风险较高或需要公开讨论的变更使用短期分支和 Pull Request。短期分支合并后删除，不建立长期 `dev` 分支。

提交格式：

```text
<type>(<scope>): <简短说明>
```

常用类型：`feat`、`fix`、`docs`、`refactor`、`test`、`chore`。

## 前端约束

- 使用 TypeScript，不无理由引入 `any`。
- 页面负责组合，跨页面业务状态进入 Pinia store 或 composable。
- API 类型集中维护，不在多个组件复制同一结构。
- 超大页面按用户任务拆分，不按视觉小块机械拆分。
- 所有异步操作都有加载、成功、空状态、失败和重试反馈。
- AI 建议界面展示原文、依据、建议文本、差异和用户决定。
- Electron 渲染进程不直接访问任意 Node.js API。

## 后端约束

- 按业务能力组织模块，不建立全局 controller/service/mapper 大目录。
- Controller 只处理协议、校验和权限，不承载业务分支。
- 应用服务负责编排，确定性规则保持独立、可测试。
- Repository 隐藏 MySQL 与 H2 的持久化差异。
- 外部输入在系统边界校验，数据库写操作明确事务边界。
- 时间持久化使用 UTC，接口使用 ISO 8601。
- 外部模型调用只通过 `ai` 模块进行。

## AI 变更

- Prompt 版本化，不把长提示词散落在业务代码中。
- 模型输出先通过 Schema，再进入业务流程。
- 固定评测材料不能包含真实个人简历或联系方式。
- 模型、提示词或输出 Schema 变化时运行固定评测和异常样例。
- AI 不负责实现或决定最终评分权重、岗位排序和面试状态转换。

## 测试层级

- 单元测试：领域规则、转换、校验和错误分支；
- 集成测试：数据库迁移、事务、模块协作和本地 API；
- 前端组件测试：关键状态、表单、差异和失败反馈；
- 端到端测试：创建项目、保存简历、生成新版本、导出和删除；
- 桌面测试：首次启动、子进程退出、数据目录、备份恢复和升级迁移。

修复缺陷时先保留可重复的复现条件，再实施最小修复并运行相关回归。

## 常用验证

前端生产构建：

```bash
cd frontend
npm run build
```

后端测试：

```bash
cd backend
mvn test
```

桌面工程建立后，应提供单一命令完成开发启动，并由持续集成构建安装包。

## 完成标准

一项变更只有同时满足以下条件才算完成：

- 验收结果可由其他人重复验证；
- 相关构建和测试通过；
- 没有新增敏感信息、密钥或真实用户数据；
- 加载、空状态、失败和恢复路径已处理；
- 数据模型或用户行为变化已更新对应文档；
- 重大取舍已记录在 `docs/decisions.md`；
- 没有混入与目标无关的重构或依赖。

## 发布要求

每个公开版本至少包含：

- 版本号和面向用户的变更说明；
- 可验证的 Windows 或 macOS 安装包；
- 对应提交或标签；
- 核心流程测试结果；
- 数据迁移与回滚说明；
- 已知问题和隐私影响说明。
