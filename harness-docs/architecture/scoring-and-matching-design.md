# 岗位评分

## 1. 设计范围

本文档当前完成 Sprint 1 的“简历多维度评分”设计。岗位匹配相似度排序同样属于 AI 禁飞区，由成员 2 在同一文档后续章节补充。

Sprint 1 的简历评分只评估简历自身质量，不直接依赖目标岗位 JD。岗位相关性和岗位缺口由岗位匹配模块负责。

## 2. 禁飞区声明

简历评分多维度权重计算属于课程 AI 禁飞区。本设计中的评分维度、分值上限、扣分条件、总分合成规则由成员 1 人工确定并实现。

AI 仅可用于整理文档结构、提示测试覆盖维度和检查表述是否清楚，不得生成评分函数、权重计算代码、可直接翻译为实现的伪代码或最终分数。

## 3. 评分目标

简历评分用于帮助求职者理解当前简历在完整度、能力证据、经历表达、量化结果和可读性上的问题。评分结果只作为修改参考，不代表录用概率，也不用于企业端筛选。

评分结果必须满足：

- 可解释：展示维度分和扣分原因；
- 可复现：相同输入和规则版本得到相同结果；
- 可审计：结果保存规则版本和输入指纹；
- 可测试：覆盖正常、缺失、边界和异常输入；
- 不编造：建议只提示补充方向，不虚构用户经历和数字。

## 4. 输入与输出

### 4.1 输入

Sprint 1 评分输入：

- `resume_versions.id`：被评分的简历版本；
- `resume_versions.content_json`：简历内容快照；
- `resume_evidence_refs`：简历版本与能力证据的引用关系；
- `capability_evidences`：被引用的能力证据。

Sprint 1 暂不依赖：

- `job_descriptions.parsed_json`：由岗位匹配模块使用，不参与基础简历评分。

### 4.2 输出

评分结果写入 `resume_assessments`，接口返回结构与数据库字段保持一致。

示例：

## 5. 评分维度与分值上限

| 维度 | 分值上限 | 看什么 | 典型问题 | 扣分触发条件 |
|---|---:|---|---|---|
| 完整度（`completeness`） | 15 | 基本信息、教育、项目/实习、技能四类核心模块是否存在 | 简历模块缺失 | 缺少核心模块时扣分 |
| 证据支撑（`evidenceSupport`） | 20 | 简历内容是否引用能力证据库中的事实 | 简历内容无事实来源 | 无证据引用；项目内容明显多于引用证据 |
| 经历质量（`experienceQuality`） | 30 | 项目/实习描述是否包含行动和结果 | 只有职责清单，没有成果 | 只有标题无行动描述；结果为空或过于模糊 |
| 量化表达（`quantitativeExpression`） | 20 | 是否有数字、百分比、规模、时间等量化指标 | “参与开发”但没有结果数据 | 项目经历通篇无任何量化信息 |
| 可读性（`readability`） | 15 | 文本长度是否合理，表达是否清晰具体 | 描述空泛、过短或过冗长 | 单个项目/实习经历描述过短、过长或内容空泛 |
| 合计 | 100 |  |  |  |

> 注：以上分值上限记录为成员 1 当前人工设计结果。后续如团队评审调整分值，必须同步更新本文档、测试表和规则版本。

### 5.1 分数封顶与合成规则

为避免同一维度多项扣分后出现负分，评分结果必须满足以下约束：

- 每个维度从该维度满分开始扣减；
- 同一维度内多项扣分可以累计；
- 每个维度的最终得分最低为 0 分，不得出现负分；
- 每个维度的最终得分最高不得超过该维度分值上限；
- 总分等于各维度最终得分之和；
- 总分最低为 0 分，最高为 100 分。

示例说明：完整度满分为 15 分，即使基本信息、教育信息、项目/实习经历和技能全部缺失，完整度最终得分也应为 0 分，而不是负分。

## 6. 评分规则人工设计表

规则版本：`resume-score-v1`  
设计人：成员 1  
日期：2026-07-08  

说明：

- 本节记录成员 1 的人工评分规则设计；
- AI 只整理格式，不补充分值、不决定扣分阈值、不生成实现逻辑；

### 6.1 完整度 `completeness`

满分：15  
满分条件：基本信息、教育信息、项目/实习模块和技能模块都存在。

| 扣分情况 | 扣几分 | 扣分原因 code | 用户提示文案 |
|---|---:|---|---|
| 基本信息缺失 | 5 | `missing_basic_info` | 基本信息缺失，无法提供真实的求职信息。 |
| 教育信息缺失 | 8 | `missing_education` | 教育信息缺失，简历完整程度大打折扣。 |
| 实习/项目经历缺失 | 10 | `missing_projects` | 没有真实的项目经历或者实习经历，经验缺失难以取得信任。 |
| 技能缺失 | 6 | `missing_skills` | 缺少相关技能的说明，无法快速了解求职者能力。 |

### 6.2 证据支撑 `evidenceSupport`

满分：20  
满分条件：所提及的项目或者实习经历都有关联的证据信息。

| 扣分情况 | 扣几分 | 扣分原因 code | 用户提示文案 |
|---|---:|---|---|
| 没有关联信息 | 20 | `no_evidence_ref` | 完全没有证据支持，无法证明简历内容真实性。 |
| 有部分关联信息 | 比例扣分，每条5分| `partial_evidence_ref` | 部分项目缺乏证据支持，建议进行补齐，提升真实性。 |
| 关联信息不可用 | 15 | `invalid_evidence_ref` | 关联信息不可用，请检查证据是否被删除或是否仍然有效。 |

人工判定口径：

- 当简历中存在多个项目/实习经历，但只有部分经历关联能力证据时，视为“有部分关联信息”；
- 被软删除、无法读取或不属于当前简历版本的证据，不计为有效关联证据；
- 证据支撑只判断事实来源是否存在，不替代经历质量和量化表达评分。

### 6.3 经历质量 `experienceQuality`

满分：30  
满分条件：项目/实习描述包含详实的行动和结果描述。

| 扣分情况 | 扣几分 | 扣分原因 code | 用户提示文案 |
|---|---:|---|---|
| 缺少项目/实习经历的行动描述 | 15 | `missing_project_action` | 缺少经历的行动描述，建议说明你具体做了什么。 |
| 缺少项目/实习经历的结果描述 | 10 | `missing_project_result` | 缺少经历的结果描述，建议补充可验证的产出、影响或结果。 |

人工判定口径：

- 行动描述：是否说明自己完成了什么具体工作；
- 结果描述：是否说明该工作产生了什么产出、效果、影响或交付物；
- 只有“参与开发”“负责项目”“熟悉技术”等泛化表述时，不能视为完整行动或结果描述。

### 6.4 量化表达 `quantitativeExpression`

满分：20  
满分条件：项目经历中包含数字、规模、时间或者结果的相关指标。

| 扣分情况 | 扣几分 | 扣分原因 code | 用户提示文案 |
|---|---:|---|---|
| 缺少量化结果 | 15 | `missing_quantitative_result` | 项目经历缺少数字、规模、时间或结果指标，建议补充已有事实中的可验证数据。 |

### 6.5 可读性 `readability`

满分：15  
满分条件：描述文本长度合适，表达清晰具体不啰嗦。

人工判定口径：

- 检查对象：单个项目/实习经历描述；
- 长度单位：中文字符数；
- 当前人工阈值：300—500 字符；
- 该阈值不是整份简历长度，也不是单条 bullet 长度；
- 若后续团队评审调整阈值，必须同步更新本文档和测试用例。

| 扣分情况 | 扣几分 | 扣分原因 code | 用户提示文案 |
|---|---:|---|---|
| 描述过短 | 10 | `description_too_short` | 描述过短，建议补充具体行动、使用技术和真实结果。 |
| 描述过长 | 5 | `description_too_long` | 描述过长，建议压缩为更清晰的要点，突出关键信息。 |

### 6.6 全局边界扣分码

| 场景 | 扣分原因 code | 用户提示文案 |
|---|---|---|
| 简历内容为空或关键结构完全缺失 | `empty_resume_content` | 简历内容为空，无法完成有效评分，请先补充基本信息、教育经历、项目/实习经历和技能信息。 |

说明：`empty_resume_content` 用于标记空简历边界场景。该场景下各维度最终得分仍遵守“最低为 0 分”的封顶规则。

## 7. 扣分原因结构

每条扣分项必须满足：

- 用户看得懂；
- 能定位问题；
- 能指导修改；
- 不编造经历；
- 不直接替用户生成虚假成果。

结构示例：

```json
{
  "code": "missing_project_result",
  "dimension": "experienceQuality",
  "reason": "项目经历缺少结果描述",
  "points": 10,
  "rule": "项目经历应包含可验证的结果描述",
  "suggestion": "建议补充可验证结果，例如完成内容、影响范围或数据规模；若暂无证据，请先补充能力证据。"
}
```

## 8. 评分版本管理

- 规则版本号：`resume-score-v1`；
- 每次评分保存 `ruleVersion`；
- 每次评分保存 `input_fingerprint`，用于去重和复现；
- 相同 `resume_version_id + ruleVersion + input_fingerprint` 命中已有记录时，返回已有评分；
- 规则更新时递增版本号，旧版本评分记录保持不变。

## 9. 边界值与异常处理

| 场景 | 处理方式 |
|---|---|
| `content_json` 为 null 或缺失 | 返回总分 0，扣分项包含 `empty_resume_content` |
| `projects` 为空数组 | 经历质量和量化表达应显著扣分 |
| `skills` 为空或缺失 | 完整度扣分，技能相关展示为空 |
| `resume_evidence_refs` 为空 | 证据支撑维度为 0 |
| 输入字段格式异常 | 返回业务错误，不写入评分结果 |
| 相同输入重复评分 | 根据 `input_fingerprint` 返回已有结果 |

# 岗位匹配

## 1. 禁飞区声明

岗位匹配算法（含维度权重配置、覆盖率计算公式、一票否决阈值、技能别名映射表、综合评分合成规则）属于课程 AI 禁飞区。本设计中的匹配维度、基础权重、覆盖率计算方式、一票否决条件、综合得分公式由成员 2 人工确定并手写实现。
AI 不得生成匹配算法核心逻辑、权重数值、技能别名映射表、覆盖率阈值或可直接翻译为实现的伪代码。

## 2. 匹配目标

岗位匹配用于帮助求职者理解自己的简历与目标岗位之间的差距。系统将简历内容与 JD 的结构化要求进行多维度对比，输出综合匹配度和各维度覆盖详情。

匹配结果必须满足：

- 可解释：展示每个维度的覆盖率、命中项、缺失项；
- 可复现：相同输入和算法版本得到相同结果（幂等）；
- 可审计：结果保存算法版本和输入指纹；
- 可测试：覆盖 JD 有/无某维度要求、简历全匹配/完全不匹配/部分匹配、空输入等场景；
- 不编造：只根据简历已有内容进行匹配判定，不虚构用户技能或经历。

匹配结果不用于企业端筛选，仅作为求职者自我评估参考。

## 3. 输入与输出

## 4. 匹配维度与权重

### 4.1 五大维度

| 维度 | 维度键 | 基础权重 | 数据来源（JD 侧） | 数据来源（简历侧） | 匹配方式 |
|---|---|---|---|---|---|
| 必备技能 | `requiredSkill` | 0.30 | `parsed.requiredSkills` | `content.skills[]` | 精确 + 别名模糊匹配 |
| 加分技能 | `preferredSkill` | 0.00 | `parsed.preferredSkills` | `content.skills[]` | 精确 + 别名模糊匹配（参考维度） |
| 经验要求 | `experience` | 0.25 | `parsed.experienceRequirements` | `content.projects[].title + description` | 字符级 bigram 重叠 |
| 学历要求 | `education` | 0.15 | `parsed.educationRequirements` | `content.education[].degree` | 等级分级匹配 |
| 职责覆盖 | `dutyCover` | 0.30 | `parsed.responsibilities` | 简历全文（技能+项目+教育） | 字符级 bigram 重叠 |

当 JD 在某维度无要求时，该维度权重自动归零，剩余权重按比例重新分配：
总有效权重 = Σ(有要求的维度权重)
各维度最终权重 = 原权重 / 总有效权重



## 5. 维度计算规则

### 5.1 必备技能 & 加分技能

匹配方式：技能标准化后集合交集匹配

标准化步骤：
1. 统一小写
2. 去除空格和连字符
3. 别名映射

别名映射表（人工维护）：

| 简历写法 | 标准化为 | JD 写法示例 |
|---|---|---|
| `Spring Boot` | `springboot` | `SpringBoot` |
| `Vue3` | `vue` | `Vue` |
| `K8s` | `kubernetes` | `Kubernetes` |
| `Node.js` / `NodeJS` | `node` | `Node` |
| `React.js` / `ReactJS` | `react` | `React` |
| `PostgreSQL` | `postgres` | `Postgres` |

计算方式：
覆盖率 = 命中数 / JD 技能总数 × 100%
维度得分 = 覆盖率 × 该维度最终权重


匹配判定：
- 标准化后集合命中 → 计入 `matchedItems`，若简历原始名 ≠ JD 原始名则记录到 `aliasMatches`
- 标准化后未命中 → 计入 `missingItems`

### 5.2 经验要求

匹配方式（v1.1.0 起）：字符级 bigram 重叠匹配。对每个 JD 经验要求文本，生成所有相邻 2-字符片段（bigram），在所有简历项目文本（标题 + 描述）中寻找最佳重叠比例。

```
重叠比例 = |JD_bigrams ∩ resume_bigrams| / |JD_bigrams|
重叠比例 ≥ 0.40 → 命中
```

示例：JD "微服务开发" → bigrams {微服,服务,务开,开发}，简历 "微服务架构设计与开发" → 交集 {微服,服务,开发} = 3/4 = 75% → 命中。

年限类关键词（含数字或"年"字）在 n-gram 未命中时归入 `unknownItems` 而非 `missingItems`。原因：简历中通常不会直接写"3年经验"，而是体现在项目时间段中，自动判定不准确，应标记为"无法判定"而非"缺失"。

> v1.0.0 历史：原使用标点分词 + 精确集合交集匹配，因中文文本几乎无法命中，经验覆盖率恒为 0%。v1.1.0 改用 bigram 重叠匹配。

### 5.3 学历要求

匹配方式：分级匹配

学历等级映射：

| 学历 | 等级值 |
|---|---|
| 大专 | 1 |
| 本科 | 2 |
| 硕士 | 3 |
| 博士 | 4 |

判定规则：
- 简历学历等级 ≥ JD 最低学历等级 → 匹配（coverage = 100%）
- 简历学历等级 < JD 最低学历等级 → 不匹配（coverage = 0%）
- 简历无学历信息 → 不匹配
- JD 学历关键词不在映射表中但简历有学历信息 → 视为匹配

说明：简历端取 `education[0].degree`（第一段教育经历的最高学历）。JD 端取所有学历要求的最低等级。例如 JD 要求"本科及以上"，最低要求为本科（等级 2），简历为硕士（等级 3）即匹配。

### 5.4 职责覆盖（参考维度）

匹配方式（v1.1.0 起）：与经验维度相同的字符级 bigram 重叠匹配。将简历全文（技能列表 + 项目标题描述 + 教育院校专业）作为独立文本片段，与 JD 职责文本逐一做 bigram 重叠计算。重叠比例 ≥ 0.40 视为命中。

> v1.0.0 历史：原使用标点分词 + 精确集合交集匹配。

## 6. 综合评分与等级划分

### 6.1 评分合成

```
加权总分 = Σ(各维度覆盖率 × 该维度最终权重)
综合匹配度 = round(加权总分)
```

### 6.2 一票否决规则

当必备技能覆盖率 < 60%时，综合匹配度封顶 40 分：

```
if (必备技能覆盖率 < 60) {
    综合匹配度 = min(加权总分, 40)
}
```

设计理由：必备技能是岗位硬性门槛，即使其他维度全部匹配，核心技能严重缺失的候选人也难以胜任该岗位。

### 6.3 封顶与保底

- 综合匹配度最低为0，最高为100
- JD 所有维度均无要求时（没有已解析的 JD 字段），返回100

### 6.4 匹配等级

| 等级 | 分数区间 | 含义 |
|---|---|---|
| 高匹配 | 80-100 | 简历与岗位核心要求高度契合，可以直接投递 |
| 中等匹配 | 60-79 | 简历基本满足要求，部分维度存在差距 |
| 低匹配 | 40-59 | 简历存在明显短板，建议针对性补充后投递 |
| 不匹配 | 0-39 | 简历与岗位要求差距较大，建议优先补充核心技能 |

## 7. 技能别名匹配

技能别名匹配用于处理同一技术的不同写法（如 `Vue3` vs `Vue`、`K8s` vs `Kubernetes`）。

规则：
- 别名映射表由成员 2 人工维护，不在算法运行时自动推测；
- 每条命中且存在别名的匹配记录在 `aliasMatches` 中，Key 为简历原始名，Value 为 JD 原始名；
- 无别名差异的匹配不记录（如简历写 `Java`、JD 也写 `Java`）；
- 后续发现新的常见别名时，由成员 2 更新映射表并同步更新本文档和测试用例。

## 8. 版本管理

- 算法版本号：`v1.1.0`（常量 `ALGORITHM_VERSION`）
- 每次匹配保存 `algorithm_version`
- 每次匹配保存 `input_fingerprint`
- 规则更新时递增版本号，旧版本记录保持不变
- 版本更新必须同步更新本文档、测试用例和种子数据
- v1.1.0 变更：经验维度和职责覆盖维度改用字符级 bigram 重叠匹配；权重重分配 — 必备技能 0.30、加分技能 0.00（参考）、经验 0.25、学历 0.15、职责覆盖 0.30

## 9. 多 JD 排序规则（按匹配度排序）

当用户有多份 JD 时，前端应支持按匹配度降序排列。

排序规则：

1. 按 `matchScore` 降序排列（匹配度高的在前）
2. 同分时按 `requiredCoverage` 降序排列（必备技能更匹配的在前）
3. 仍同分时按 `created_at` 降序排列（最新的在前）

排序实现位置：前端/API 层，不属于匹配算法核心，不在禁飞区范围内。

## 10. 边界值与异常处理

| 场景 | 处理方式 |
|---|---|
| JD 未解析（`parseStatus != "succeeded"`） | 返回 422 `JD_NOT_PARSED`，提示先调用 parse 接口 |
| JD 不存在或不属于当前用户 | 返回 404 `JOB_DESCRIPTION_NOT_FOUND` |
| 简历版本不存在 | 返回 404 `RESUME_VERSION_NOT_FOUND` |
| `resumeVersion.content` 中 `skills` 为空数组 | 技能维度覆盖率全部为 0 |
| `resumeVersion.content` 中 `projects` 为空数组 | 经验维度覆盖率全部为 0 |
| `resumeVersion.content` 中 `education` 为空数组 | 学历维度 coverage 为 0 |
| JD `parsed.requiredSkills` 为空 | 必备技能覆盖率默认 100（无要求即满分） |
| JD 所有维度均无要求 | 返回 100 分 |
| 完全相同的输入重复请求 | 幂等返回已有结果，不重新计算 |
| `input_fingerprint` 计算失败 | 抛出 `IllegalStateException`，不写入 DB |
| `details` JSON 序列化失败 | 抛出 `IllegalStateException`，事务回滚 |
