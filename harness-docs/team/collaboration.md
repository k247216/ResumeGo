# 团队协作流程

本文档规定「职达」团队如何使用 GitLab、Issue、Merge Request、AI 日志和每日节奏推进开发。

## 1. 基本原则

1. 先对齐范围，再开始开发。
2. 每个任务必须有负责人和验收标准。
3. 三名成员都必须写代码、做 Review、留下过程证据。
4. 禁飞区核心实现必须人工完成。
5. 每天让 `dev` 分支保持可运行。
6. 不把敏感信息、密钥或完整简历原文提交到仓库。

## 2. 分支规则

```text
main        稳定演示版本
dev         日常集成版本
feature/*   功能开发分支
bugfix/*    缺陷修复分支
bug-injection/* Bug 注入演练分支
```

规则：

- 不直接向 `main` 提交代码；
- 不直接向 `dev` 提交业务代码；
- 功能从 `dev` 拉 `feature/*`；
- 完成后通过 Merge Request 合并到 `dev`；
- Sprint 验收通过后由 `dev` 合并到 `main`。

## 3. Issue 流程

Issue 用来说明“要做什么”。

每个 Issue 至少包含：

- 目标；
- 范围；
- 非目标；
- 负责人；
- 验收标准；
- 是否涉及 AI 禁飞区；
- 是否允许使用 AI；
- 测试要求；
- 对应分支。

## 4. Commit 规范

格式：

```text
type(scope): 简短说明
```

常用类型：

- `feat`：新功能；
- `fix`：修复；
- `test`：测试；
- `docs`：文档；
- `refactor`：重构；
- `chore`：工程配置。

示例：

```text
feat(resume): 增加简历草稿创建接口
test(match): 增加岗位匹配边界用例
docs(team): 补充协作流程
```

## 5. Merge Request 规则

MR 用来说明“这段代码能不能合并”。

合并到 `dev` 前必须满足：

1. 关联 Issue；
2. MR 描述清楚变更；
3. 本地能运行或对应测试通过；
4. 至少一名非作者 Review；
5. QA 检查测试证据；
6. AI 使用日志已填写；
7. 禁飞区变更有人工设计和人工实现说明。

## 6. Review 规则

推荐 Review 关系：

| 作者 | Review | 测试/验收 |
|---|---|---|
| 成员 1 | 成员 2 | 成员 3 |
| 成员 2 | 成员 1 | 成员 3 |
| 成员 3 | 成员 2 | 成员 1 |

Review 重点：

- 是否符合 Issue 范围；
- 是否越过 MVP 边界；
- 是否破坏模块边界；
- 是否有敏感信息；
- 是否有测试证据；
- 是否符合 AI 禁飞区规则。

## 7. 每日节奏

建议节奏：

```text
09:15  站会：昨天/今天/阻塞
09:30  更新 GitLab Issue Board
11:30  每人至少 push 一次当前分支
16:30  处理当天可合并 MR
17:00  dev 分支集成演示
17:20  QA 更新 bug、测试结果和 AI 日志
```

站会控制在 15 分钟。超过 15 分钟的问题，由 SM 拆出来单独处理。

## 8. Sprint 1 推荐推进

1. PO 固定文档结构和 S1 范围；
2. SM 搭建前后端和数据库基础骨架；
3. QA 建立 AI 日志、测试基线和结构化校验；
4. 成员 1 实现简历和评分；
5. 成员 2 实现岗位和匹配；
6. 成员 3 实现 AI 适配和测试；
7. 三人串联基础闭环；
8. QA 完成 Bug 注入检测记录；
9. PO 依据验收标准确认 S1 演示。
