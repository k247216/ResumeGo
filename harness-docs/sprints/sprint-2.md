# Sprint 2｜求职工作台与双闭环

## 1. Sprint 目标

Sprint 2 的目标是在 Sprint 1 基础逻辑闭环之上，完成“求职工作台”雏形，并形成两个最小可演示闭环：

```text
闭环 1：简历优化迭代
简历评分 / 岗位匹配
→ AI 定向建议
→ 用户采纳建议
→ 生成新的简历版本
→ 查看新版本

闭环 2：模拟面试最小版
选择简历版本和目标岗位
→ 启动模拟面试
→ 状态机推进 3 轮问答
→ AI 评价回答
→ 生成面试总结和改进建议
```

本 Sprint 以“工作台主流程”和“可解释闭环”为第一目标，不建设完整社区、登录注册、岗位推荐平台或复杂面试系统。

## 2. Sprint 范围

### 本 Sprint 必须完成

- 求职工作台主入口；
- 真实岗位数据集的最小接入；
- 岗位数据扩展字段设计与 seed 数据导入；
- 简历建议采纳后生成新版本；
- 简历版本列表与版本切换；
- 模拟面试会话数据结构；
- 模拟面试最小状态机；
- AI 面试问题生成、回答评价和总结建议；
- 千问 Max 调用稳定性与 Mock 降级；
- S2 Smoke Test、AI 日志和禁飞区验收记录。

### 本 Sprint 明确不做

- 登录注册、短信、OAuth；
- 简历社区、帖子、评论、点赞；
- 大规模岗位爬虫；
- 自动投递；
- 多岗位推荐排序；
- PDF 导出；
- 语音、视频、数字人面试；
- 复杂追问策略；
- 向量数据库、消息队列、微服务。

## 3. 产品形态

S2 前端主入口从 S1 的分散功能页收束为“求职工作台”：

```text
求职工作台
├── 简历优化
│   ├── 当前简历版本
│   ├── 最近评分
│   ├── AI 建议
│   └── 采纳后生成新版本
├── 岗位匹配
│   ├── 真实岗位数据
│   ├── 目标岗位选择
│   └── 匹配结果与缺口
└── 模拟面试
    ├── 绑定当前简历版本和岗位
    ├── 3 轮问答
    ├── 单题评价
    └── 最终总结建议
```

原有能力证据、简历、JD 页面可以保留为深层页面或辅助页面，但不再作为主演示入口。

模拟面试入口采用“上下文优先，入口兜底”原则：

- 从求职工作台进入时，面试绑定当前简历版本和目标岗位，页面展示已绑定上下文卡片，不再提供自由切换表单；
- 直接从导航进入模拟面试时，由于缺少上游上下文，保留简历版本和目标岗位选择表单作为兜底；
- 面试一旦创建，简历版本和岗位视为本次面试计划的固定快照，后续复盘、历史记录和新版本生成都围绕该快照展开。

- 测试：成员 3

### S2-06｜模拟面试数据表与会话接口

- 主责：成员 2

### S2-07｜人工状态机驱动面试流程

- 主责手写：成员 1

- Review：成员 2

### S2-08｜AI 面试问题、评价与总结接入

- 主责：成员 3

- 真实 API 失败时有 Mock 降级或可理解错误。

## 5. 模拟面试最小状态机

S2 暂不做复杂追问。最小状态如下：

```text
READY
→ ASKING
→ WAITING_ANSWER
→ EVALUATING
→ NEXT_QUESTION
→ ASKING
→ WAITING_ANSWER
→ EVALUATING
→ NEXT_QUESTION
→ ASKING
→ WAITING_ANSWER
→ EVALUATING
→ SUMMARIZING
→ COMPLETED
```

异常状态：

```text
FAILED
CANCELLED
```

人工规则：

- 每场面试固定 3 题；
- `READY` 只能启动到 `ASKING`；
- `WAITING_ANSWER` 收到回答后进入 `EVALUATING`；
- `EVALUATING` 完成后，如果未满 3 题进入 `NEXT_QUESTION`；
- 已满 3 题进入 `SUMMARIZING`；
- 总结生成后进入 `COMPLETED`；
- `COMPLETED`、`FAILED`、`CANCELLED` 不允许继续回答；

## 6. 当前多轮面试前端实现边界

当前前端已将模拟面试产品形态调整为“一次面试包含多轮面试官”的整体体验：

- 面试大厅选择多位面试官后，先创建后端 `interview_plans`，再按顺序启动每一轮单面试官会话；
- 历史区按“一次面试记录”展示：同一 `interview_plans` 下的多个面试官会话合并为一条记录；没有计划归属的旧 session 不进入历史列表，避免把无法归属的旧数据误展示为一次完整面试；
- 面试记录优先展示绑定岗位的公司图标，并同时展示绑定的简历版本，便于后续比较同一岗位下不同简历版本的面试表现；
- 从求职工作台进入面试时，简历版本和目标岗位被锁定；如需更换，用户需要返回工作台调整，避免在面试页破坏“当前版本针对当前岗位验证”的闭环；
- 直接从导航进入模拟面试时仍保留简历和岗位选择表单，用于无上下文创建面试计划；
- 整次多轮面试完成前，不允许直接从面试流程返回简历工作台；
- 整次多轮总结入口只在多轮计划完成后展示；
- 已删除“提示、跳过本题、提前结束本轮”等入口，避免超出当前人工状态机范围。

当前限制与后续开发：

- “删除面试记录”目前采用后端计划软删除：`interview_plans.deleted_at` 标记隐藏，原始 session、问答和评价数据保留，避免误删验收数据。
- 后端已新增 `interview_plans` 作为“一次多轮面试”的容器，并通过 `interview_sessions.plan_id`、`round_order` 绑定每位面试官轮次。
- 旧的未绑定 session 暂不展示在历史列表；如需迁移，需要由成员人工判断历史 session 之间是否属于同一次面试，不能由前端猜测。
- 当前实现不修改 `InterviewStateMachine`、状态转换表和每轮问答推进规则；每一轮仍然复用原有单面试官 session 状态机。
- 跳过题目、提前结束本轮、追问策略都属于面试状态机扩展，必须由成员人工设计状态转换表和测试后再实现，AI 不参与生成状态机代码。
- AI 只生成问题、评价和总结，不决定状态转换。

### 面试版本绑定原则

S2 面试记录绑定的是“某一份简历版本快照 + 某一个目标岗位”，而不是可被覆盖的简历本体。

推荐链路：

```text
岗位 A + 简历版本 v2.3
→ 创建一次多轮模拟面试
→ 查看复盘和简历改进建议
→ 采纳后生成简历版本 v2.4
→ 用岗位 A + 简历版本 v2.4 再开一次面试
→ 对比 v2.3 与 v2.4 的表现变化
```

这样可以保证面试历史、简历版本和岗位目标之间的关系可追溯，也方便验收时解释“面试反馈如何反哺简历迭代”。

## 7. 岗位数据处理原则

S2 岗位数据采用：

```text
原文优先
→ 核心字段抽取
→ 扩展字段暂存
```

核心字段：

- 岗位名称；
- 公司名称；
- JD 原文；
- 必备技能；
- 加分技能；
- 工作职责；
- 经验要求；
- 学历要求。

扩展字段：

- base / 城市；
- 薪资；
- 岗位类型；
- 来源平台；
- 来源链接；
- 行业；
- 公司规模；
- 采集时间；
- 标签。

扩展字段先存入 `source_meta_json`，暂不参与 S2 匹配算法。

## 10. Definition of Done

S2 完成必须同时满足：

- 求职工作台主链路可演示；
- 真实岗位数据可选择；
- 采纳建议后能生成新简历版本；
- 旧版本不可变；
- 模拟面试能完成 3 题并生成总结；
- AI 调用有结构化校验和审计日志；
- Mock 降级可用或错误提示清晰；
- 状态机禁飞区具备人工设计、测试和逐行讲解证据；
- 三名成员都参与代码、测试或 Review。
