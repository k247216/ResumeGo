# 架构决策记录（ADR）

重要决策必须说明背景、选择、替代方案和后果。状态使用：
`Proposed`、`Accepted`、`Superseded`。

---

## ADR-001｜从示例仓库切换为职达项目基线

- 日期：2026-07-06
- 状态：Accepted

### 背景

仓库原有 Go、Gin、GORM 内容仅用于展示 `.agent` 项目记忆结构，并非职达已经确认的
技术方案。

### 决策

删除示例架构语义，以“面向求职者的 AI 简历与求职助手”为唯一项目上下文。后续代码
和文档不得继续引用示例项目假设。

### 后果

项目正式进入设计阶段；在技术栈确认前不生成大规模业务代码。

## ADR-002｜优先采用课程 Web 基线技术栈

- 日期：2026-07-06
- 状态：Accepted

### 背景

课程选题材料为 W2 推荐 Vue 3、Spring Boot 3 和 PostgreSQL/MySQL。使用统一技术栈
可以降低环境、辅导和验收风险。

### 决策

使用 Vue 3 + TypeScript + Spring Boot 3 + MySQL 8。后端采用模块化单体，部署使用
Docker Compose + Nginx。

### 替代方案

- Go + Gin：团队熟悉时开发效率高，但偏离课程基线。
- Python Agent 应用：适合独立 Agent 项目，不适合作为本项目完整 Web 后端的默认方案。
- PostgreSQL：同样满足课程要求，但团队已选择 MySQL。

## ADR-006｜首个 AI 模型采用通义千问 Max

- 日期：2026-07-06
- 状态：Accepted

### 背景

团队已经具备通义千问的使用条件，课程准备清单也要求申请阿里云百炼 API Key。

### 决策

首个模型供应商采用阿里云百炼，模型使用通义千问 Max。模型调用统一收口到 `ai` 模块，
通过内部接口向业务模块提供能力；业务代码不得直接依赖供应商 SDK。

模型名称、Endpoint 和密钥通过配置注入，不硬编码到业务代码。具体模型标识在接入时以
阿里云控制台实际可用值为准。

### 后果

MVP 阶段只接入一个模型，降低调试和评测成本；保留 OpenAI 兼容的适配接口，未来可以
增加其他模型而不修改简历、匹配和面试模块。

## ADR-007｜Sprint 1 使用固定演示用户

- 日期：2026-07-06
- 状态：Accepted

### 背景

Sprint 1 的核心目标是验证简历、JD、评分、匹配和 AI 定向优化闭环。完整注册登录会
占用开发和测试时间，但不会直接证明核心产品价值。

### 决策

Sprint 1 不实现注册、登录、Token 刷新和复杂权限。系统启动时创建一个固定演示用户，
业务数据仍保留 `user_id` 归属。应用通过统一的当前用户接口提供演示用户 ID，业务模块
不得直接写死具体数值。

### 后果

核心闭环能够优先交付；后续增加 Spring Security 时，只需替换当前用户提供方式，不必
修改简历、岗位和 AI 审计表的归属关系。

## ADR-008｜Sprint 1 只完成最小基础逻辑闭环

- 日期：2026-07-06
- 状态：Accepted

### 背景

项目周期短，Sprint 1 的首要任务是证明核心业务链路成立，而不是提前完成文件解析、
复杂交互、模板和产品化能力。

### 决策

Sprint 1 只实现以下最小闭环：

```text
结构化录入经历和简历
→ 粘贴一个 JD
→ 手写规则完成评分与匹配
→ 调用千问 Max 生成一次定向建议
→ 采纳建议并产生新简历版本
```

只实现支撑该闭环的最小页面、数据表、AI 审计和自动化测试。不实现真实登录、文件导入、
PDF 导出、模拟面试、多岗位推荐、复杂模板和产品化视觉打磨。

### 后果

Sprint 1 能够尽早暴露数据模型、禁飞区算法和 AI 结构化输出问题。非核心功能进入后续
Sprint，不能以“顺手实现”为由进入 Sprint 1。

## ADR-003｜采用模块化单体而非微服务

- 日期：2026-07-06
- 状态：Accepted

### 背景

实训周期只有 12 天，核心风险是业务闭环、AI 质量和工程验收，而不是分布式扩展。

### 决策

采用前后端分离的模块化单体。通过模块接口保持边界，不引入服务发现、消息中间件或
分布式事务。

### 后果

部署、调试和 Bug 注入定位更简单；未来确有必要时再拆分模型调用或 PDF 导出服务。

## ADR-004｜以能力证据库连接四个核心模块

- 日期：2026-07-06
- 状态：Accepted

### 背景

如果简历优化、岗位匹配、模拟面试和反馈分别保存数据，产品会退化为四个孤立工具。

### 决策

建立能力证据库，保存用户事实性的项目、实习、竞赛和技能证据。简历要点、岗位匹配、
面试问题和反馈均引用这些证据。

### 后果

AI 建议可以溯源并降低经历编造风险，同时形成真正的反馈闭环。

## ADR-005｜AI 提供建议，确定性程序负责最终控制

- 日期：2026-07-06
- 状态：Accepted

### 决策

AI 可以解析文本、生成表达和提供评价，但评分权重、匹配排序、状态转换、权限和数据
一致性由手写程序控制。所有模型输出先通过 Schema 和业务规则校验。

### 后果

系统结果更可解释、可测试，也满足课程 AI 禁飞区要求。

## ADR-009｜Sprint 3 将面试复盘沉淀为计划级产物

- 日期：2026-07-15
- 状态：Accepted

### 背景

S2 的模拟面试已经能够完成单轮问答和评价，但历史记录容易按单个 session 分散展示，
用户难以理解“一次多轮面试”的整体表现。用户也希望面试结果可以反哺简历迭代，而不是
只停留在一次聊天总结。

### 决策

Sprint 3 将 `interview_plan` 作为一次完整面试的容器。每位面试官对应一个
`interview_session`，计划层负责组织轮次、保存整次复盘和生成成长趋势快照。

整次复盘只有在 plan 下所有 session 均为 `COMPLETED` 后才能生成。复盘结果写入
`interview_plans.summary_json`，成长趋势写入 `interview_growth_snapshots`。

计划层不实现、不修改面试状态机。状态集合、转换表、题号推进和结束条件仍属于人工
状态机禁飞区。

### 替代方案

- 继续按 session 分散展示历史：实现简单，但不符合真实多轮面试心智。
- 手动勾选多个历史 session 生成综合总结：灵活但容易混合不同岗位、不同简历版本。
- 让 AI 根据对话决定是否结束本次面试：违反面试状态机禁飞区。

### 后果

产品心智更清晰，历史记录以“一次面试”为单位复看；成长趋势有稳定后端快照来源；
后续可围绕 plan 建立更完整的复盘、训练和简历迭代能力。

## ADR-010｜公司偏好 Profile 只作为 AI 建议上下文

- 日期：2026-07-15
- 状态：Accepted

### 背景

项目希望后续结合真实大厂岗位要求、潜在偏好和不同公司的表达风格，增强简历建议的
真实感。但如果直接将公司偏好用于评分、排序或录用概率，会破坏禁飞区边界并制造不可靠
结论。

### 决策

新增 `company_profiles` 作为公司偏好 Profile 预留表，当前种子数据均标记为
`experience_based`。Profile 只进入 AI 建议 Prompt，用于调整建议关注点和表达风格。

Profile 不参与：

- 简历评分；
- 岗位匹配排序；
- 录用概率判断；
- 状态机控制；
- 事实断言。

### 后果

可以逐步增强 AI 建议的产品真实感，同时保留安全边界。后续若接入官方资料或岗位数据集，
需要补充来源说明和人工审核流程。

## ADR-011｜Sprint 3 采用本地单用户工作区令牌保护

- 日期：2026-07-16
- 状态：Accepted

### 背景

Sprint 1 使用固定演示用户是为了快速验证 MVP 闭环。进入 Sprint 3 后，系统已经保存
简历版本、岗位绑定、面试回答原文、AI 评价和成长趋势快照。如果继续对所有 API 完全
放行，任何知道接口和会话 ID 的请求都可能读取或操作本地面试数据。

### 决策

当前阶段不引入完整注册登录、JWT、RBAC 或多租户体系，而是将职达定位为本地单用户
求职工作台，采用 Local Workspace Token 作为无感访问保护。

- 后端 dev 环境默认绑定 `0.0.0.0`，方便团队成员联调和临时演示；
- 前端所有业务 API 请求自动携带 `X-Workspace-Token`；
- 后端对 `/api/**` 请求统一校验本地工作区令牌；
- 令牌来自环境变量，默认仅用于本地开发演示；
- 用户不需要登录，数据仍归属于固定 demo user；
- 该机制不参与评分、岗位排序、面试状态机或 AI 输出判断。

### 替代方案

- 继续全部 API 放行：实现最简单，但不适合保存面试回答和评分后的 S3 阶段。
- 完整账号登录系统：安全边界更完整，但会引入注册、密码、Token 刷新和权限模型，
  当前阶段成本高且偏离核心求职闭环。

### 后果

产品体验保持“打开即用”，同时通过本地工作区令牌避免 API 完全裸奔。团队联调或临时
演示时必须同步配置非默认 `LOCAL_WORKSPACE_TOKEN`。如果只希望本机访问，可显式设置
`SERVER_ADDRESS=127.0.0.1`。后续若进入真实在线部署，可将 Local Workspace Token
平滑替换为 JWT、Session 或 OAuth，业务接口只需复用同一安全入口。
