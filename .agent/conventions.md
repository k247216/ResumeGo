# 职达工程规范

## 1. 总体原则

- 先写验收标准，再写实现。
- 一个 Issue 对应一个明确目标；一个 PR 尽量只解决一个问题。
- 不允许无约束 Vibe Coding。
- AI 生成内容必须经过人工审查和测试。
- 三个 AI 禁飞区遵守 `.agent/no-fly-zone.md`。

## 2. Git

### 分支

- `main`：稳定分支，只通过 Merge Request 合入。
- `dev`：Sprint 集成分支。
- `feature/<issue>-<name>`：功能分支。

### Commit

格式：`<type>(<scope>): <中文描述>`

类型包括 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`。

示例：

```text
feat(resume): 添加简历版本创建接口
test(matching): 覆盖必备技能缺失的排序规则
docs(no-fly): 补充面试状态机转换说明
```

涉及 AI 禁飞区的提交在正文中增加：

```text
No-Fly-Zone: assessment
Authored-By: human
```

## 3. Java 后端

- 包名全小写，类名大驼峰，变量和方法名小驼峰。
- 按业务模块组织代码，禁止创建全局 `controller/service/mapper` 大目录。
- Controller 不包含业务分支。
- Service 不返回数据库实体。
- 外部输入在系统边界完成校验。
- 禁止忽略异常；业务异常使用稳定错误码。
- 数据库写操作明确事务边界。
- 时间统一存储为 UTC，接口使用 ISO 8601。

## 4. Vue 前端

- 使用 TypeScript，禁止无理由使用 `any`。
- 页面负责组合，业务状态进入 Pinia store 或 composable。
- API 类型集中定义，不在多个组件复制接口结构。
- 用户可见的 AI 内容必须展示加载、失败、重试和来源状态。
- AI 修改建议必须提供原文、建议文本、理由和采纳/拒绝操作。

## 5. AI 集成

- Prompt 必须版本化，禁止把长 Prompt 散落在业务代码中。
- 模型输出先做 Schema 校验，再进入业务流程。
- 不信任模型生成的分数、排序、ID、权限结论和状态跳转。
- AI 失败不得导致用户已保存的简历内容丢失。
- Prompt 或模型变更必须运行固定评测集。

## 6. 测试

- 禁飞区采用测试先行，至少覆盖正常、边界、空值和异常路径。
- 修复 Bug 时先增加能够复现问题的测试。
- 外部模型调用在单元测试中使用固定响应，不访问真实 API。
- 集成测试验证数据库约束和模块协作。
- 核心用户闭环必须有端到端 Smoke Test。

## 7. 日志与隐私

- 使用结构化日志，不用 `System.out` 或 `console.log` 代替正式日志。
- 不记录原始简历、面试回答、手机号、邮箱、访问令牌和模型密钥。
- AI 审计日志与开发 AI 使用日志分开保存。
- 对外错误信息不得暴露堆栈、SQL 或供应商密钥。

## 8. Definition of Done

任务完成必须同时满足：

- 验收标准全部通过；
- 自动化测试通过；
- 无新增敏感信息泄露；
- API 和数据模型变更已更新文档；
- AI 参与情况已记录；
- 禁飞区变更可由作者逐行讲解；
- 至少一名非作者完成 Review。
